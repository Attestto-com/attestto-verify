## The three things most likely to bite you

### 1. pkijs picks the leaf certificate POSITIONALLY

`CertificateChainValidationEngine` concatenates `[...trustedCerts, ...certs]`,
dedupes, and validates whatever ends up **last** as the end entity
(`pkijs/build/index.es.js` around line 14929 in 3.4.0). This is undocumented and
can change on a dependency bump.

`chain-validator.ts` therefore builds `certs: [...intermediates, signerCert]` and
the ordering is load-bearing. Do not "tidy" that array. There is a runtime guard
immediately after `engine.verify()` that compares `certificatePath[0]` against the
signer by raw DER and refuses to report `trusted: true` if they differ. If a pkijs
upgrade ever breaks the positional assumption, that guard turns a silent
authentication bypass into a visible failure, which is why it exists at runtime and
not only in a test.

**The bypass is real and is pinned as a test.** Anchoring one level higher in the
hierarchy makes pkijs return `true` for a forged signer, and for a pool with no
signer in it at all. See the last case in `chain-validator.cr-anchor.spec.ts`.

### 2. Coverage is ratcheted, and it will block your push

`pnpm coverage:check` runs from `.githooks/pre-push` and in CI. Coverage may rise,
never fall.

- Raise the bar after adding tests: `pnpm coverage:update`, then commit `coverage-baseline.json`.
- **Generate the baseline on the Node version in `.nvmrc` (22).** `nvm use` first.
- Never hand-edit `coverage-baseline.json`. Lowering it is what the NO-DROP rule rejects.
- Emergency bypass is `git push --no-verify`. CI runs the same gate, so this defers
  the failure rather than avoiding it.

There is a cautionary tale attached. The first version of the ratchet downgraded a
FLOOR failure to a warning whenever the running Node major differed from the
baseline's, to avoid an unreproducible local red. The baseline was generated on
Node 25 and CI runs Node 22, so on CI every FLOOR breach became a warning and the
gate could not fail. `gate-self-test` caught it on the first run by seeding a
deliberate violation and observing that `coverage:check` passed anyway. **A gate
that cannot fail is worse than a gate that occasionally fails confusingly.** The
measured coverage turned out to be identical on both majors, so the guard was
protecting against nothing.

Corollary worth internalising: **run the CI job locally before pushing.** Under the
`.nvmrc` Node version, in CI's order: changelog gate, `pnpm install --frozen-lockfile`,
`pnpm gate-self-test`, `pnpm run lint`, `pnpm test`, `COVERAGE_BASE_REF=origin/main pnpm run coverage:check`,
`pnpm run build`, then the `pnpm pack` tarball check.

### 3. Trust is resolver-only. There is no bundled fallback

`CLAUDE.md` used to describe a `src/trust-store/` of bundled CR roots and a
resolver-unreachable fallback. That directory does not exist and
`no-bundled-trust.regression.spec.ts` actively forbids importing `@attestto/trust`
anywhere in `src/`, because doing so bundles every promoted country's `ALL_CERTS`
into the worker (roughly 1 MB gzipped of PEM shipped to every visitor, the 2026
regression). The doc was corrected in `d189150`.

The model: the resolver returns key **fingerprints**; the validator matches the CA
certificates **the PDF itself embeds** against those fingerprints and uses the match
as the pkijs trust anchor. If nothing matches, the chain stays unverified and the
signature does not reach `verified`. **Failing closed is the design.** There is
nothing to fall back to, and adding one would breach the security floor.

Consequence: a PDF that embeds only the signer leaf has no candidate anchor at all,
so no `did:pki` is derivable and the resolver is never contacted. That path is
currently silent and undifferentiated. Tracked as ATT-1282.

- `gate-self-test: OK (proven able to fail: lint, test, coverage:check)`.
- The CR fix was confirmed **end to end against the live resolver**, not only against
  the engine: a real chain returns `trusted: true` anchored at
  "CA SINPE - PERSONA FISICA v2" with `trustSource: 'resolver'`, and a forged signer
  is rejected with an error that names the real reason.
- The Ed25519 forgery was reproduced before it was fixed (10 of 40 messages accepted
  with an all-zero key and all-zero signature) and re-run afterwards to confirm the
  rejection, with a genuine keypair round trip proving legitimate signatures still
  verify.

## Open work, in priority order

Full detail is in the tickets; this is the shape and the reasoning.

1. **ATT-1279 (Bug): `gatePluginLevel()` is never called in production.** The
   ATT-312 crypto floor in `pdf-verifier.ts:494` is referenced only by its own
   spec. It is thoroughly unit-tested and wired to nothing. Note also that
   `PdfSignatureInfo.level` admits `'verified'` and `'signed'` while the gate only
   downgrades `'trusted' | 'qualified'`, so wiring it up alone is not sufficient.
   The separate floor in `plugins/registry.ts` **is** wired and does work.
2. **ATT-1280: cover the verdict path.** `level = 'verified'` in `pdf-verifier.ts`
   has no coverage for the PAdES path, and `certificate-parser.ts:1069-1112`, the
   sole assignment site of `cryptographicallyVerified`, is at 0%. Change the `&&`
   on the level ladder to `||` today and the whole suite stays green. This is the
   highest-risk gap in the repo.
3. **SOC-256 residual: `attestto-self-sign.ts` is 0%** and is never round-tripped
   against the verifier, so nothing proves which fields are actually inside the
   canonical signed bytes. The producer and verifier must agree byte for byte or
   every prior signature stops verifying.
4. **ATT-1281: `resolver-revocation.ts` is 0%** with three fail-open defaults. It
   already takes an injectable `fetchFn`, so there is no harness work first.
   `signatureVerified: data.signatureVerified !== false` reports an unverified
   response as verified if the field is ever renamed.
5. **ATT-1282: decide what a leaf-only CR PDF should do**, and pin it. Recommended:
   keep failing closed, but say so distinctly instead of showing the same yellow
   state as "resolver unreachable".
6. **ATT-1283: stand up a DOM test environment.** All four Lit components are at 0%,
   roughly 4,838 lines, about 73% of the coverage deficit, because
   `environment: 'node'` is set globally in `vite.config.ts`. **Schedule this rather
   than discover it:** with the ratchet live, the first person to touch a component
   needs the harness before they can push. Two pure decision points inside those
   files (the level-to-status map and the document verdict that fires the public
   `verification-complete` event) can be extracted and table-tested without mounting
   anything, and that captures most of the risk cheaply.

`src/components/` was deliberately **not** excluded from coverage. Excluding it would
have moved the headline number by roughly 30pp while removing no risk.

## Conventions worth knowing before you commit

- **`CHANGELOG.md` must be updated for any `src/**` change**, and must contain no
  em-dashes (U+2014). Both are enforced by `scripts/ci-changelog.mjs`.
- **Any new quality gate must be registered in `package.json` under `gateSelfTest`**
  with a seed that violates it. `scripts/gate-self-test.mjs` writes the seed, runs
  the gate, and requires a non-zero exit, then requires zero on a clean tree. An
  unregistered gate is exactly the decorative control that file exists to prevent.
  It earned its place on this branch, twice: once by design and once by catching the
  author's own broken gate.
- `prepare` runs `npm run build` **first and unconditionally**, then installs the git
  hooks. The build must stay first: a git-dependency install depends on it, and
  `scripts/install-git-hooks.mjs` exits 0 on every failure path so a hook problem can
  never break a consumer's install.
